Frontend
Interactive map interface

The Next.js + React frontend lets users click on a map of NYC to set pickup and dropoff points. It calls the prediction API in real time and displays the estimated fare and duration. Route visualization is powered by OSRM (Open Source Routing Machine), which calculates the actual road path between the two points.

System Design
Technical architecture

The system runs fully inside Docker. Prediction requests from the frontend are validated and enqueued by a FastAPI + Uvicorn backend, placed into a Redis job queue, and picked up by an async worker that runs the ML model inference. Results are returned via Redis and sent back to the client.

Architecture diagram — from the presentation
Full system architecture inside Docker
🖥 Next.js Frontend
React UI with interactive map. Sends trip details (coordinates, datetime, passengers) to the API and displays prediction results and OSRM route.
⚡ FastAPI + Uvicorn
Validates incoming requests and enqueues jobs into Redis. Exposes a /predict endpoint documented with Swagger / OpenAPI.
🗄 Redis
Acts as both the job queue and the result store, decoupling the API from the ML inference worker for async processing.
🤖 Worker + Models
Python worker pulls jobs from Redis and runs inference on two LightGBM models — one for fare, one for duration — then writes results back to Redis.
Deployment
Docker — three containers running

The full stack runs with a single docker compose up: the backend (FastAPI on port 8000), the prediction worker, and Redis (port 6379). Everything is containerized and reproducible.

API
Swagger — /predict endpoint

The prediction API accepts trip coordinates, datetime, passenger count and distance via a POST request and returns predicted fare in USD and trip duration in minutes. The endpoint is fully documented with Swagger UI generated automatically by FastAPI.

ML Models
Training, iteration & final metrics

Multiple model versions were trained and compared — from v1 to the final pipeline trained on April–June 2022 data. LightGBM consistently outperformed other algorithms across both tasks. Feature engineering included Haversine distance calculated with GeoPandas, time-based features from the pickup datetime, and vendor/passenger metadata.

Other algorithms evaluated included XGBoost, Linear Regression, KNN, Random Forest and Decision Trees before landing on LightGBM as the best performer for both fare and duration targets.
